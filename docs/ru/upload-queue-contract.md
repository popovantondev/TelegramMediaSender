# Внутренний контракт очереди отправки

Этот документ описывает общий формат плана для вкладок «Медиакомплекты», «Учёба по неделям» и импорта StudyArchivePrep. Это внутренний формат Telegram Media Sender. Внешний JSON `publication-plan-v1` не меняется.

## Состав плана

- `mode`: `media_groups`, `weekly_study` или `publication_plan`.
- `root`: папка, относительно которой проверяются файлы плана.
- `profile_id`, `account_id`, `chat_id`: получатель, к которому привязана очередь.
- `publication_project_id`, `publication_revision`: заполняются у импортированного плана.
- `items`: неизменяемый упорядоченный список текстовых сообщений и вложений.

Каждый элемент имеет уникальный ключ, тип, позицию и состояние в журнале. Для файла дополнительно сохраняются исходный путь, относительный путь, имя, размер, время изменения и SHA-256. `group_key` обозначает комплект или раздел таблицы. `operation_key` связывает элементы, отправляемые одним сетевым запросом.

Позиция в `items` — источник истины. Исполнитель, интерфейс, журнал и восстановление не сортируют элементы повторно.

## Границы отправки

- Текст и одиночный файл — самостоятельные операции.
- Видео и аудио медиакомплекта отправляются в существующем порядке отдельными сообщениями.
- Субтитры отправляются документами альбомами до десяти файлов. У каждого вложения свой элемент журнала, сохранённый ID запроса и ID сообщения Telegram.
- После возобновления формируются только операции из элементов, которые ещё не подтверждены и не пропущены по решению пользователя.
- Импортированный план отправляется в порядке, предоставленном экспортёром. Ни сортировка по неделям, ни перегруппировка здесь не применяются.

У альбома ID запроса и подтверждения связываются с каждым вложением. Если ответ Telegram содержит лишь часть результата или не пришёл, операция сохраняется как неопределённая до сверки; подтверждённые вложения не отправляются повторно без решения. Сбой соединения повторяет операцию с теми же сохранёнными ID. После частичного восстановления оставшиеся элементы отправляются отдельно, чтобы не дублировать альбом.

## Совместимость с недельным журналом

Сохранённый план старого формата трактуется как `weekly_study`; отсутствующие поля группы и операции остаются пустыми. Сериализация прежнего недельного плана должна сохранять прежнюю идентичность, чтобы очередь продолжалась в существующих строках журнала.

Расширенные поля сериализуются только для новых режимов. SQLite использует схему версии 2. При открытии базы версии 1 приложение сначала создаёт согласованную резервную копию, затем транзакционно добавляет поля режима и операций. Старые очереди остаются недельными и продолжают читаться.

## Получатель, повторы и состояние

Сравнение очереди использует идентификаторы профиля, аккаунта и чата. Название профиля и чата отображается человеку, но не служит ключом восстановления.

Вложение считается отправленным только после сохранённого подтверждения Telegram. Имя и размер файла в истории чата — кандидаты совпадения, а не проверка содержимого. При неполном совпадении пользователь выбирает, пропустить элемент или отправить его снова. Одно сообщение Telegram нельзя назначить нескольким элементам.

Неопределённая попытка сначала сверяется с историей и использует сохранённые ID запроса. Запуск приложения не отправляет очередь автоматически. Любое продолжение требует проверки получателя и отдельного подтверждения.

## Условия готовности общего контракта

- Все три источника плана создают общую структуру без потери порядка.
- Разбиение альбомов известно до начала сетевых запросов.
- Журнал восстанавливает каждое вложение отдельно.
- Существующий недельный журнал открывается без изменения его снимка.
- Импортированный план сохраняет проект, редакцию, текст, ID и контрольные суммы файлов.
- Никакой пользовательский путь отправки не обходит общий журнал и исполнитель очереди.
